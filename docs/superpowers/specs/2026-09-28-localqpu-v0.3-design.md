# localqpu v0.3 설계

- 작성일: 2026-09-28
- 기반: v0.2.1. Codex와 함께 정한 우선순위(2026-09-28): HTTP 수준 장애 주입과 요청 기록 → 작업 조회·관리 API.

## 1. HTTP 수준 장애 주입

### 문제
v0.2의 시나리오는 접수된 작업의 결말(실패·취소·대기)만 바꾼다. 이 도구의 목적인 "양자 API를 부르는 주변 코드" 검증에는 전송 계층 실패(일시적 5xx, 429, 느린 응답, 끊긴 연결, 처리됐지만 유실된 응답)가 더 자주 필요하다.

### 확인한 클라이언트 동작 (qiskit-ibm-runtime 0.50.0 `api/session.py`)
- 재시도 대상 상태: 500·502·503·504·520·521·522·524. POST도 이 목록이면 재시도한다(IBM이 안전을 보장한다는 주석). 기본 총 5회, 연결 재시도 3회, backoff 0.5.
- 429는 재시도 목록에 없다 → 사용자 코드가 직접 처리해야 한다.

### 결정
- 시나리오 최상위에 `http_faults` 목록을 추가한다. 항목:
  - `path`(필수, fnmatch 패턴, 예 `/api/v1/jobs/*/results`), `method`(선택, 없으면 모든 메서드)
  - `times`(기본 1): 이 규칙을 적용할 요청 수. 목록 순서대로 처음 맞는 규칙이 소비된다.
  - `status`(100–599), `retry_after`(초, `Retry-After` 헤더), `message`
  - `drop_connection`: 응답 없이 연결을 끊는다(클라이언트는 연결 오류).
  - `delay_seconds`: 응답 전에 기다린다. status·drop이 없으면 "느린 정상 응답"이다.
  - `phase`: `before`(기본, 처리하지 않고 실패) 또는 `after`(정상 처리한 뒤 응답만 실패 → 유실된 응답·중복 제출 재현).
- 제어 API(`/_localqpu/*`)에는 장애를 적용하지 않는다(테스트가 항상 복구할 수 있도록).
- 소비 상태는 시나리오 상태에 두고 reset으로 되돌린다. `GET /_localqpu/scenario`는 남은 횟수를 보여 준다.

## 2. 요청 기록

- `GET /_localqpu/requests`: 최근 요청 1000개(`method`, `host`, `path`, `status`, `fault`, `duration_ms`, `time`). 본문·헤더·쿼리는 기록하지 않는다(자격 증명 노출 방지). 제어 API 요청은 기록하지 않는다.
- 테스트가 재시도 횟수와 순서를 단언하는 용도다. 예: 503 두 번 뒤 `POST /api/v1/jobs`가 3번 기록됐는지.
- reset은 요청 기록도 비운다.

## 3. 작업 조회·관리 API

### 확인한 클라이언트 동작 (qiskit-ibm-runtime 0.50.0)
- `service.jobs(...)`: `GET /api/v1/jobs`에 `limit`·`offset`·`backend`·`pending`(true/false)·`program`·`tags`·`session_id`·`created_after`·`created_before`·`sort=ASC`(ascending일 때)와 `exclude_params=true`. 응답 `{"jobs": [...], "count": 전체 개수}`를 받아 페이지를 넘기며 모은다.
- `job.metrics()`: `GET /jobs/{id}/metrics`. `job.usage()`는 `usage.status`가 `pending`이면 0, 아니면 `usage.qpu_charge_time_seconds`. `job.properties()`는 `timestamps.running`으로 보정값 시점을 고른다.
- `job.logs()`: `GET /jobs/{id}/logs`의 본문 텍스트.
- `job.update_tags(tags)`: `PUT /jobs/{id}/tags` 본문 `{"tags": [...]}` → **204**여야 성공, 이어서 작업을 다시 조회해 `tags`를 읽는다.
- `service.delete_job(id)`: `DELETE /jobs/{id}`, 404는 `RuntimeJobNotFound`.
- 제출 본문의 `tags`(job_tags 옵션)와 `private`는 작업 조회 응답의 `tags`·`private`로 돌아와야 한다.

### 결정
- 작업 관리자에 실행 시작 시각(`running_at`)과 메타데이터 갱신·작업 삭제를 추가한다. 태그·private는 작업 메타데이터에 둔다(작업 관리자는 IBM 개념을 모른다).
- 목록은 IBM 작업만(Braket 작업 제외) 기본 최신순으로, `sort=ASC`면 오래된 순으로 돌려준다. 태그 필터는 요청한 태그를 모두 가진 작업만 고른다(실제 IBM 의미는 미확인).
- metrics: `timestamps`(created·running·finished), `usage`(끝나면 `status: "final"`, 시뮬레이터라 `qpu_charge_time_seconds: 0`, 아니면 `pending`), `bss.seconds: 0`.
- logs: 생성·대기열 이탈·종료와 실패 사유를 한 줄씩 적은 평문.
- 범위 밖: 작업 입력(params) 보관(메모리 증가 방지 때문에 대기열을 벗어나면 비운다 → `job.inputs`는 빈 값), `/workloads`(0.50에 공개 호출 경로 없음).
