# localqpu v0.2 설계

- 작성일: 2026-09-27
- 기반: v0.1 설계서(`2026-09-27-localqpu-design.md`), PyPI v0.1.0
- 범위(추천 순서대로 진행): Estimator → Session/Batch → GHCR 이미지 → 노이즈 → AWS Braket → executor stub
- 각 절은 해당 기능을 구현하기 직전에 클라이언트 동작을 확인한 뒤 채운다.

## 1. 시뮬레이션 한도 기준 변경: "활성 큐비트" → "얽힌 큐비트"

### 문제
v0.1은 barrier·delay를 뺀 연산이 걸린 큐비트를 모두 "활성"으로 셌다. 새 executor Estimator는 관측량을 재려고 칩 전체(127큐비트)에 측정을 붙이므로, 실제로 얽힌 큐비트는 2개인데 127개로 세어 한도(24)에 걸렸다(2026-09-27 확인).

### 결정
- 한도(`--max-sim-qubits`)는 **여러 큐비트 게이트로 서로 얽힐 수 있는 큐비트 수**(`entangled_qubits`)로 판단한다. 두 개 이상의 큐비트에 걸린 연산(barrier 제외, 제어 흐름 연산 포함)의 큐비트를 센다.
- 정확 계산은 **Aer MPS(matrix_product_state)**로 한다. 얽히지 않은 큐비트는 곱 상태라 비용이 거의 없어, 127큐비트 폭에 2큐비트만 얽힌 회로가 0.01초에 계산된다(실측). 한도 안에서는 절단 없이 정확하다.
- 이름 변경: `ProgramOutput.active_qubits` → `entangled_qubits`, 제어 API 작업 요약의 `active_qubits` → `entangled_qubits`. v0.x이므로 호환 별칭은 두지 않고 변경 기록에 적는다.

## 2. Estimator

### 확인한 클라이언트 동작 (qiskit-ibm-runtime 0.50.0)
- 기존 `EstimatorV2`: `program_id="estimator"`. params의 PUB은 `[회로(QPY), 관측량(dict: Pauli 문자열 → 계수), 파라미터 값, precision]`이고 `EstimatorPub.coerce(tuple(pub), precision)`로 복원된다. 기본 정밀도는 `options.default_precision`.
- 새 executor 기반 `Estimator`: `program_id="executor"`에 `semantic_role="estimator_v2"`. 측정 결과를 받아 기대값 계산은 **클라이언트가** 한다. 따라서 localqpu는 executor 경로가 넓은 측정 회로를 계산하기만 하면 된다(1절로 해결).

### 결정
- `programs/estimator.py` 추가: sampler와 같은 두 단계 해석(직렬화 실패는 버전 안내, 구조 오류는 본문 수정 안내).
- 정확 계산: `qiskit_aer.primitives.EstimatorV2`를 MPS 방식으로 실행한다. precision이 없으면 정확한 기대값(표준편차 0), 있으면 Aer가 그 정밀도의 정규분포 잡음을 더한다.
- 한도 초과: 모양만 맞춘 stub(기대값은 [-1, 1] 균등 무작위, 표준편차는 요청 정밀도 또는 0), 메타데이터에 `localqpu_stub: true`.

## 3. Session/Batch

### 확인한 클라이언트 동작 (qiskit-ibm-runtime 0.50.0)
- 생성: `POST /api/v1/sessions` 본문 `{mode: "dedicated"|"batch", backend, max_ttl?}` → 응답의 `id`만 읽는다.
- 조회: `GET /api/v1/sessions/{id}` → `state`(`open`·`active`·`closed`), `accepting_jobs`, `mode`, `backend_name`, `max_ttl`, `interactive_ttl`, `started_at`, `closed_at` 등. `Session.status()`는 `open`→"Pending", `active`+accepting→"In progress, accepting new jobs", `closed`→"Closed"로 바꾼다. `Session.from_id`는 `backend_name`과 `mode`가 있어야 한다.
- 닫기(`close()`): `PATCH /api/v1/sessions/{id}` 본문 `{accepting_jobs: false}`. 404는 무시한다.
- 취소(`cancel()`): `DELETE /api/v1/sessions/{id}/close` — 세션의 작업을 모두 취소한다.
- 작업 제출: `POST /jobs`에 `session_id`가 붙는다. 닫힌 세션은 primitive 계층이 먼저 "The session is closed."(`IBMRuntimeError`)로 막는다(`Session._run` 자체에는 검사가 없어 처음엔 없다고 잘못 판단했고, 계약 테스트로 바로잡음). 작업 조회 응답의 `session_id`를 작업 객체에 저장한다.

### 결정
- `sessions.py`: 메모리 세션 관리자. 상태는 생성 시 `open`, 첫 작업 제출 시 `active`, 닫기·취소 시 `closed`(accepting_jobs=false).
- 제출 검증: 모르는 세션은 400, 닫힌 세션이나 다른 백엔드로의 제출은 409. 파이썬 클라이언트는 닫힌 세션을 스스로 막지만, 직접 모드·비-Python 클라이언트를 위해 서버도 검사한다. 404를 쓰지 않는 이유: 클라이언트가 제출 404를 "Program not found"로 바꿔 오해를 부른다.
- 세션 취소는 그 세션의 끝나지 않은 작업을 모두 취소한다.
- 작업 조회 응답과 제어 API 작업 요약에 `session_id`를 넣고, 제어 API reset은 세션도 비운다.
- 범위 밖: 세션 만료(max_ttl·interactive_ttl) 흉내, 세션 사용량 집계.

## 4. GHCR 이미지

### 결정
- `.github/workflows/docker.yml`: `main` 푸시·PR에서는 이미지를 빌드하고 컨테이너를 띄워 (1) HEALTHCHECK가 healthy가 되는지, (2) 권한 없는 사용자(uid 10001)로 도는지, (3) 실제 Qiskit 클라이언트로 두 Sampler가 결과를 받는지(`tests/contract/test_container_smoke.py`)를 검사한다. 로컬 Docker 없이 매 푸시마다 이미지가 검증된다.
- `v*` 태그에서만 amd64·arm64 이미지를 `ghcr.io/ictechgy/localqpu`에 `{version}`, `{major}.{minor}`, `latest` 태그로 게시한다. 게시 작업만 `packages: write` 권한을 가진다.
- Dockerfile: 권한 없는 사용자로 실행, `/_localqpu/health` HEALTHCHECK 추가(CI 서비스 컨테이너·compose의 준비 판단용).
- 확인 필요: GHCR 패키지의 첫 게시 후 공개 여부. 개인 계정 패키지는 처음에 비공개로 만들어질 수 있어, 첫 릴리스 뒤 패키지 설정에서 공개로 바꿔야 할 수 있다(미확인).

## 5. 노이즈 흉내

### 확인한 사실 (2026-09-27 실측)
- `NoiseModel.from_backend(FakeBrisbane)`(0.6초)를 Aer MPS에 넣으면 127큐비트 폭 ISA Bell 회로가 0.3초에 돌고, 4000샷 중 약 6%가 `01`·`10`(게이트·판독 오류)으로 나온다. 같은 노이즈의 Estimator ZZ는 0.97.

### 결정
- 시나리오 최상위에 `"noise": true|false`(기본 false)를 추가한다. 테스트마다 켜고 끌 수 있게 시나리오에 둔다.
- 작업 제출 시점의 시나리오로 정한다: 노이즈가 켜져 있으면 `ExecutionSettings.noise_backend`에 작업의 백엔드 이름을 넣는다.
- 노이즈 모델은 `qiskit_ibm_runtime.fake_provider`의 같은 칩 스냅샷(`ibm_brisbane` → `fake_brisbane`)으로 만들고 백엔드별로 캐시한다.
- sampler는 노이즈가 켜져 있으면 유휴 큐비트 압축을 하지 않는다(노이즈 모델이 물리 큐비트 번호 기준). estimator·executor는 원래 칩 폭 그대로 계산하므로 노이즈 모델만 더한다.
- stub 경로는 노이즈와 무관하다.

## 6. AWS Braket (실험적)

### 확인한 사실 (amazon-braket-sdk 1.127.2, botocore Braket 모델)
- Braket 패키지는 **Python 3.11 이상**만 지원한다 → `localqpu[braket]` 선택 설치로 두고, 3.10에서는 관련 테스트를 건너뛴다.
- REST(rest-json) 경로: `POST /quantum-task`(201, `quantumTaskArn`), `GET /quantum-task/{arn}`, `PUT /quantum-task/{arn}/cancel`, `GET /device/{arn}`, `POST /devices`. ARN은 경로에 퍼센트 인코딩돼 온다. 상태 값: CREATED·QUEUED·RUNNING·COMPLETED·FAILED·CANCELLING·CANCELLED.
- 결과는 작업의 `outputS3Directory/results.json`을 S3 `GetObject`로 읽는다. Braket은 버킷 이름이 `amazon-braket-`로 시작해야 한다.
- `AwsSession`은 S3 클라이언트를 내부에서 `boto_session.client("s3")`로 만들어 접속 주소를 바꿀 공개 인자가 없다 → 하위 클래스로 `s3_client`를 덮어쓴다. 기본 버킷을 주면 STS(계정 ID 조회)를 부르지 않는다.
- 서버 쪽 계산은 `braket.default_simulator.StateVectorSimulator`가 Braket OpenQASM을 직접 해석해 `GateModelTaskResult`를 만든다(최대 26큐비트).

### 결정
- 장치는 SV1 시뮬레이터(`arn:aws:braket:::device/quantum-simulator/amazon/sv1`) 하나. 능력(capabilities)은 기본 시뮬레이터의 것을 쓴다.
- 작업은 기존 작업 관리자에 `program_id="braket-openqasm"`으로 넣어 대기열·시나리오(next_jobs·failures·queue)를 그대로 공유한다. 사용자 취소·재시작 동작도 IBM 쪽과 같다.
- S3 경로 `GET /amazon-braket-*/<key>`로 완료된 작업의 `results.json`을 돌려준다. 이때 `taskMetadata.id`·`deviceId`를 작업 ARN·장치 ARN으로 바꾼다. 없으면 S3 형식의 XML `NoSuchKey`(404).
- 오류는 AWS 형식(`{"__type": "...Exception", "message": ...}`)으로 돌려준다.
- `localqpu.connect_braket(port)`: 가짜 자격 증명·us-east-1의 boto3 세션, localqpu를 가리키는 Braket·S3(path 방식) 클라이언트, 기본 버킷 `amazon-braket-localqpu`를 갖춘 `AwsSession`을 돌려준다. IBM 쪽과 같이 NO_PROXY에 호스트를 더한다.
- 한도: 기본 시뮬레이터의 26큐비트 한도를 넘으면 입력 오류로 실패한다(Braket stub은 범위 밖). 시드 고정은 지원하지 않는다(시뮬레이터가 시드를 받지 않음).
- 범위 밖: QPU 장치, 아날로그 해밀토니안(AHS) 프로그램, Braket Jobs(하이브리드 작업), 태그 API.
